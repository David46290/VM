# Histogram 特徵與分群方法

## 先講定位：這是探索，不是分類

目前路線是 explore：沒有預先定義好的標籤，所以本質是**無監督分群（clustering）**，不是分類（classification）。核心問題不是「這張屬於哪一類」，而是：

- 用什麼特徵描述一張圖？
- 用什麼距離衡量兩張圖有多像？
- 距離多近算同一群？（門檻要靠實驗調出來）

解碼和 goroutine 只是配角，上面三件事才是專案的真正難度。

## Histogram 函式的規格（Phase 1）

- 輸入：一個 `image.Image`。
- 輸出：一個 `map[uint32]float64`，每個 key 是量化後的顏色格、value 是「落在該格的像素佔全圖的比例」。（原先規劃寫 `[]float64`，實作改採稀疏 map，只存非零格。）
- 正規化：全部 value 總和 ≈ 1.0。沒有正規化，不同尺寸的圖沒法互相比較。
- 逐像素取色用 `img.At(x, y).RGBA()`，不需要知道底層型別是 YCbCr 還是 RGBA（見 `go_pitfalls_checklist.md`）。

## 必須自己做的三個設計決定

### 1. 聯合 histogram vs 各通道分開算

| 做法 | 維度範例 | 優點 | 缺點 |
|---|---|---|---|
| R、G、B 各算 1D 再串起來 | 3 × 16 = 48 | 簡單、每個 bin 樣本多 | 看不到顏色組合（「紅+白同時出現」這種資訊遺失） |
| 3D 聯合 histogram | 4×4×4 = 64 或 8×8×8 = 512 | 抓得到顏色組合 | bin 太多會稀疏（多數 bin 是 0 或雜訊） |

第一版求簡單能跑，選哪個都可以，但要能說出理由，之後可以換掉重測。


#### 1_1. 測試RGB通道位元深度與histogram解析出bin量的關係

**目前決定：先採用 3D 聯合 histogram。** 理由是聯合 key 保留的資訊最多：之後想改看各通道分開的 marginal histogram，可以從聯合 key 用位移／遮罩把 R、G、B 分量個別抽出來加總；反過來先存分開的 histogram，就合併不回聯合分佈。

**實作現況（2026-10-21）**：

- 每個通道保留高 `channel_bit` 個 bit（從 `RGBA()` 的 16-bit 值直接右移 `16 - channel_bit`），再依 R、G、B 順序打包成一個 key：R 在最高位段、G 在中間、B 在最低位段，key 總寬度為 `3 * channel_bit` bits。
- 計算過程先累積 `map[uint32]int`（key → 像素 count），再正規化成 `map[uint32]float64` 對外回傳（見下）。存檔時先把 key 排序再逐行寫出，所以同一張圖重跑、或原圖與複製檔，產出的文字檔可以直接逐行比對。
- 不同 bit 設定輸出到不同目錄、檔名也帶 bit 數（目前程式的格式為 `output/debug/histogram_4_bits_each_rgb_norm/..._4_bits_each_rgb_norm.txt`；先前 bit 實驗的目錄是 `histogram_<b>_bits_each`），避免不同參數的特徵混在一起互相污染。
- `channel_bit` 合法範圍目前設 1–10（上限 10 是因為 `3 * 10 = 30` bits 還塞得進 `uint32`，再大 key 打包會溢位），啟動時由 `check_settings()` 先檢查。
- 後續加入 `hist_key_decode`：用打包時相同的位移量右移、再用遮罩 `(1 << channel_bit) - 1` 取出各通道的量化階級，是打包的逆運算（可用 round-trip 重組回原 key 自我驗證）。通道在 key 中的位置改用三個獨立變數（R=2、G=1、B=0）表達，不再用字串 map 查表（效能原因見下方效能備忘）。
- 存檔時用 `bright_percentage` 把通道階級除以最大階級（\(2^{channel\_bit}-1\)）換成 0–1 的比例方便肉眼判讀，輸出格式為 `RGB: (r, g, b), contribution: v`（v 目前印到小數 5 位），目錄後綴為 `_bits_each_rgb_norm`。注意 `bright_percentage` 是「顏色座標」的縮放，**不是** histogram 正規化，兩種 normalize 不要混為一談。
- **正規化設計（里程碑，2026-10-21）**：`img_histogram` 內部仍逐像素累積 int count、並以 `hist_count_inspect` 驗證總和等於寬 × 高，但對外一律回傳正規化後的 `map[uint32]float64`，把它定為全專案唯一標準表示。理由：下游每個函式只需認一種型態，不必為 `map[uint32]int` 與 `map[uint32]float64` 各寫一份複製邏輯，也避免呼叫端忘了轉換而混用 count 與比例。代價是原始 count 與總像素數在離開 `img_histogram` 後不可逆地遺失，之後若需要圖片尺寸，應在特徵 struct 另外記錄。
- 正規化作法：`hist_normalize` 以「count 的實際總和」為分母逐格相除，不使用寬 × 高；如此即使之後改為取樣或只算局部區域，總和仍由資料本身保證為 1。轉換後再由 `hist_normalize_check` 以常數 `epsilon = 1e-9` 驗證所有比例總和 ≈ 1.0（浮點比較不用 `==`）。

**實驗紀錄（2026-10-21）**：樣本圖 `20230826_233548.jpg`，固定同一張圖、只改 `channel_bit`，統計產出檔案的行數（即實際出現過的 distinct key 數）：

| channel_bit | 每通道階數 \(2^b\) | 理論格子數 \((2^b)^3 = 8^b\) | 實際 distinct key 數 | 實際成長倍率 |
|---|---|---|---|---|
| 2 | 4 | 64 | 37 | — |
| 3 | 8 | 512 | 173 | 約 ×4.7 |
| 4 | 16 | 4,096 | 879 | 約 ×5.1 |
| 5 | 32 | 32,768 | 4,354 | 約 ×5.0 |
| 6 | 64 | 262,144 | 19,392 | 約 ×4.5 |

觀察：

- 理論格子數每多留 1 bit 就 ×8（推導見下方），但實際 distinct key 只成長約 ×5。因為自然照片的顏色不是均勻散佈在整個 RGB 立方體裡：大量格子根本沒有像素落入，而 map 只存非零的格子，所以實際數永遠小於理論上限，且照片顏色越集中、差距越大。
- bit 太少時格子過度合併：2 bit 時第一格（key `0x00`，即三通道都落在最低階）一格就佔了 1,813,492 個像素，本來不同的暗色全被併成同一格 → 之後分群會「把不像的誤判成像」。
- bit 太多時同一個顏色家族被切碎：5–6 bit 時，鄰近色被拆到大量相鄰格子，兩張視覺上很像的照片可能因 JPEG 雜訊／光線小偏移而落在不同格 → 距離被高估，「把像的誤判成不像」。
- 分群品質就是在上面兩種錯誤之間取捨，沒有標準答案，要靠 Phase 2 的距離報告實測決定。

**目前定案狀態**：`channel_bit = 4` 為暫定候選，程式目前也設為 4（879 格對這張圖算是「有解析度又不稀疏」的位置）。實驗與除錯過程中曾暫用 2 做 key decode 對照與熱迴圈效能測試，但它不是目前的執行設定。4 仍只是暫定，正式定案要等 Phase 2 距離報告出來、人工判讀過後再拍板。

**公式推導：為什麼理論格子數是 \(8^b\)**

設每個通道保留 \(b\) 個 bit：

1. 一個通道能表示的階數是 \(2^b\)（例如 \(b=4\) 時有 16 階：0–15）。
2. 三個通道互相獨立組合，總組合數是三者相乘：\(2^b \times 2^b \times 2^b = 2^{3b}\)。
3. 而 \(2^{3b} = (2^3)^b = 8^b\)，所以看起來像「8 的指數」——那個 8 其實是「3 個通道 × 每通道翻倍」合併寫的結果：每多留 1 bit，每個通道的階數翻倍，三通道組合就翻 \(2 \times 2 \times 2 = 8\) 倍。
4. 這也解釋了 key 的總寬度為什麼是 \(3b\) bits：key 裡 R、G、B 各佔 \(b\) bits，\(2^{3b}\) 種組合正好對應 \(3b\) 個 bit 能表示的數量。

另一個等價的看法：每多留 1 bit，等於把 RGB 顏色立方體沿每一軸再對切一刀，每個舊格子被切成 \(2^3 = 8\) 個新格子。這就是為什麼 bit 數只從 2 加到 5（+3），格子數卻從 64 暴增到 32,768（\(8^3 = 512\) 倍）——指數成長的來源是三個軸同時細分。


#### 1_2. Key decode 與紅／藍主體對照（2026-10-21）

動機：key 用 16 進制印出時，一個 hex 數字是 4 bit，而通道寬度（例如 2 bit）與它不對齊，一格 hex 會跨兩個通道，肉眼無法判讀哪個通道高。解法是寫 `hist_key_decode` 把 key 拆回三通道階級再輸出成 `(R, G, B)` 形式。讀 key 的原則：先在腦中換成「每通道一格」的階級表示（2 bit 時即把 6-bit key 每 2 位切一段），左到右依序是 R、G、B，值越大代表該通道越強。

對照實驗：`channel_bit = 2`，比較紅色主體 `20230904_002238.jpg`（約 1204 萬像素）與藍色主體 `20230901_154340.jpg`（約 1603 萬像素）。兩圖總像素不同，以下以佔全圖比例比較：

| 通道階級 (R, G, B) | 意義 | 紅圖占比 | 藍圖占比 |
|---|---|---|---|
| (3, 0, 0) | 純強紅 | 約 8.9%（1,070,086） | 約 0.3%（50,941） |
| (0, 0, 2) | 中強純藍 | 近乎 0（91） | 約 1.9%（306,070） |
| (0, 0, 1) | 暗藍 | 約 5.0%（598,712） | 約 15.8%（2,532,841） |
| (0, 0, 0) | 近黑 | 約 51.5% | 約 13.9% |

結論：

- 紅／藍主體的訊號在 2 bit 下量得出來：紅圖在 R 高、B／G 低的格子明顯居多，藍圖在 B 相對高的格子明顯居多，「純強紅」與「中強純藍」幾乎是單邊出現的簽名格。
- 但兩圖含量最大的都是 (0,0,0) 近黑與三通道相近的中性灰格，屬於背景／陰影而非主體——再次印證「已知陷阱」裡的背景主導問題，之後判讀距離報告時要先想到它。
- 單格盯著看只能看簽名格；要一眼看懂整張圖的通道傾向，下一步應該把聯合 histogram 按通道加總成 marginal 分佈（每個通道各 \(2^{channel\_bit}\) 格的占比），這也是 Phase 2 距離計算的暖身。

### 2. Bin 怎麼切

- `RGBA()` 回傳的是 **16-bit**（0–65535），不是 Python 習慣的 0–255。
- 要想清楚怎麼把 0–65535 映射到 bin 編號（位移或除法，自己推導一次）。
- 這是本階段最容易踩的坑，踩到正好學起來。

### 3. 迴圈範圍

用 `Bounds().Min` 到 `Bounds().Max` 掃描，**不要假設圖片從 (0,0) 開始**。這是 Go `image` 和 PIL/numpy 思維差最大的地方之一，先養成習慣。

## 已知陷阱（Phase 2 判讀時對照）

1. **背景主導特徵**：模型照片的背景（桌面、白牆、布）可能佔 60% 以上像素。兩隻不同模型在同一張桌上拍，histogram 可能比同一隻模型換背景拍還像。若 Phase 2 發現最近的配對都是「同背景」，就是這個兇手。之後的可能對策（先知道就好，別先做）：中心裁切、忽略接近背景色的 bin、換 HSV 只看色調等。
2. **空間資訊遺失**：histogram 只看顏色比例、不看位置。「紅白配色 A 模型」和「白紅配色 B 模型」比例一樣就會被併群；同一個模型換角度、換光線可能被拆群。這是方法的先天上限，探索階段就是要量出這個上限在哪。
3. **光線與白平衡**：同一隻模型在不同燈光下，整體顏色會偏移。Histogram 對這件事沒有抵抗力，先觀察影響多大再說。

## 距離函式（Phase 2）

- 第一版用最簡單的：兩條 histogram 逐 bin 相減取絕對值再加總（L1 距離）。正規化後，兩張完全相同的圖距離為 0，完全不重疊時距離最大為 2，心裡先有這個尺度感。
- 產出不是分群結果，而是**報告**：最近 10 對、最遠 10 對的檔名，人工對照照片判讀。
- 其他距離（histogram intersection、chi-square、Bhattacharyya 等）是之後調參的選項，現在不用先學。

Phase 2 要回答的問題（結論記得寫回這裡）：

- [ ] 最近的配對像在哪裡？（色調／背景／同一個模型？）
- [ ] 最遠的配對差在哪裡？
- [ ] 有沒有「不該像卻很近」的配對？兇手推測是？

## 特徵快取（Phase 3）

- 特徵算完存成檔案（JSON/CSV 先求有），每筆至少包含：檔案路徑 + histogram 向量。
- 分群、換距離、調門檻都只讀這份檔案重跑，不要重新解碼原圖。
- 這份檔案也是之後驗證 goroutine 版正確性的對照組（平行版結果排序後要跟它一致）。

## 效能備忘（順序在正確性之後）

- **縮圖先於 histogram**：histogram 只看顏色分佈，把圖縮到例如 128×128 再算，特徵幾乎不變，速度和記憶體差幾十倍。這是效能的第一個大槓桿，比 goroutine 還優先。
- 目前逐像素 `img.At()` 呼叫介面是慢的，但 Phase 1 先求正確，優化（縮圖、直讀像素緩衝）留到量測後再做。掃描順序目前是 x 在外、y 在內（沿欄掃），之後量到瓶頸時也是候選項目。
- **熱迴圈不要查 map（已實測）**：原本通道位置存在 `map[string]int`，打包 key 時每個像素要查 3 次字串 map。`images/` 約 60 張、每張 1200–1600 萬像素，整批約 8 億像素、等於約 24 億次查表。改成迴圈外就固定的變數後，在 `channel_bit = 2` 的整批測試中實測快了約 10 秒。教訓：迴圈裡沒有小開銷，只有被乘上億次的開銷；查表還會阻止編譯器把值在迴圈外算好。原理與速查條目見 `go_pitfalls_checklist.md`。
- 量測紀錄要帶齊：設定（`channel_bit`）、圖數量、改前與改後總時。這次的紀錄只有差值（約 10 秒），沒有留下改前／改後的絕對時間，下次 benchmark 要補齊，不然之後比較縮圖、goroutine 的效果時沒有基準。程式目前已用 `time.Now`／`time.Since` 量整批處理時間。
